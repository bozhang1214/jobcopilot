# 评估报告（v0.1.0）

> 本报告由 `jobcopilot eval --level 12` 的真实输出整理，可**零成本复现**（不需要 API Key）。
> 数据为 2026-09-15、内核 v0.1.0 的实测结果。

---

## 1. 为什么要有评估

提示词是这个项目的核心资产，而**提示词退化是不报错的**：改动一个章节号或一句措辞，
分析照样「成功」返回七段内容，只是质量悄悄变差。所以需要三层评估来把退化变成可见的
失败。

| 层 | 需要 LLM | 成本 | 跑什么 | 谁跑 |
|---|---|---|---|---|
| **L1** 程序化断言 | 否 | 0 | 结构 / 统计口径精确比对 / 段落非空 / 输出与提示词声明的 JSON 骨架一致 | 每次 CI |
| **L2** 基线回归 | 否 | 0 | **提示词指纹** + 各指标不得低于基线 | 每次 CI |
| **L3** LLM 评审 | 是 | 很低（全量 ≈180 次调用） | 覆盖度 / 是否编造 / 可执行性 / 赛道合理性 / 薪资有据 | PR 作者本地跑并附报告 |

> **CI 刻意只跑 L1+L2**：把 LLM Key 放进 CI 既有泄露风险，费用也不可控。
> 详见 [`CONTRIBUTING.md`](../CONTRIBUTING.md) §2。

数据集规模已超过计划 §3.3 的下限（20/10/15）；文件名**不带条数**（计划里写的是
`agent_dev_20.json` 这种形式），因为实际条数更多，带数字会让文件名与内容不符——
规模下限由 `tests/test_evals.py::test_load_datasets` 断言守着。

**多样性是刻意做的**：三个批量集合计覆盖了 `classify_role` 的全部 **8 个方向桶**
（评测/质量、安全、算法/模型、架构师/Leader、产品经理、运营/策略、研发/工程、其他）。
分布越复杂，`stats_exact_match` 才越难被「碰巧对上」——否则这条断言接近白给。

### 2.2 L3（真 LLM）实测 —— 2026-09-15 首次真跑

命令：`jobcopilot eval --level 123 --provider deepseek`（耗时 **275 秒**，全量约百次调用，成本 < 1 元）。

| L3 维度 | 均分（满分 5） | 含义 |
|---|---|---|
| `actionability` | **4.67** | 建议是否可执行 |
| `groundedness` | **4.33** | 是否编造（防幻觉） |
| `jd_coverage` | 4.00 | 是否覆盖 JD 关键要求 |
| `track_coverage` | 4.00 | 赛道划分是否合理 |
| `salary_anchored` | **3.67** | 薪资区间是否有依据（最低，符合预期：数据集里有 4 条**故意不给薪资**） |

**真跑立刻暴露了 stub 永远测不出的东西**：8 个单职位用例里有 **1 个失败**——
`single-无薪资` 的 `interview_qa` 段落为空。这不是崩溃，而是设计内的降级：

- 单步 LLM 调用失败/返回脏 JSON 时，该步降级为空结构并记 error 日志
  （`core/analyzers/single.py`）；
- 工具层会把空段落汇总成 `warnings` 返回给调用方（`mcp/tools.py`），全空才报错；
- 所以系统行为正确，是 **L1 的 `sections_complete` 断言在真模型下抓到了质量信号**。

**两个由此明确的重要事实**（会误导人的那种）：

1. **L1+L2 的 100% 是「构造性」的**：CI 用 `SkeletonStubLLM` 跑，它永远返回骨架，
   因此 `sections_complete` 恒为 100%。**L1+L2 守的是结构没有回归，不是模型质量。**
   质量信号只在 L3 出现——这就是为什么改提示词必须附 L3 报告。
2. **基线必须保持「stub 口径」**：真 LLM 那次与基线比对会报
   「整体通过率下降 0.975 < 1.0」，因为**两者不可比**。所以这里**刻意没有**
   用 `--update-baseline` 把真 LLM 结果写进基线——那会把「允许 12.5% 段落缺失」
   固化进零成本门禁，反而放松了守门员。真 LLM 的分数只作为**趋势**记录在本报告里。

各断言通过率：

| 断言 | 通过率 | 说明 |
|---|---|---|
| `schema_valid` | 100% | 输出 JSON 可解析、字段齐全、类型正确 |
| `stats_exact_match` | 100% | `company_distribution` / `role_distribution` / `hot_keywords` 与**程序计算**结果完全一致 |
| `job_count_match` | 100% | `job_count` == 实际职位数 |
| `sections_complete` | 100% | 单职位七段都非空 |
| `prompt_schema_conformance` | 100% | 输出与提示词里声明的 JSON 骨架一致 |

**其中最有价值的是 `stats_exact_match`**：统计是程序算的、不是模型生成的，所以可以被
**精确断言**。模型一旦「顺手改写」了统计数字，L1 立刻失败——这类幻觉在实际使用里最难
靠肉眼发现。

## 3. 怎么复现

```bash
pip install -e '.[dev]'
jobcopilot eval --level 12                    # L1+L2，零成本
jobcopilot eval --level 123 --provider deepseek   # 加上 L3（需 DEEPSEEK_API_KEY）
```

## 4. 这份报告的局限（请不要过度解读）

1. **数据集已达到计划规模（22/12/17 + 8 个单职位用例），但仍不算大**：
   「100% 通过」证明的是**结构与统计口径没有回归**，**不能**证明「分析质量好」
   ——后者要靠 L3 与人工评审。数据本身是**脱敏改写的合成样本**（不是真实抓取），
   目的是覆盖结构变异，不追求市场分布的真实性。
2. **L3 分数只作趋势看，不进门禁**：均分应在**同一模型版本内**可比、跨模型版本不可比；
   本报告已记录 2026-09-15 的首次真跑（见 §2.2），但它**不进基线**（原因见上）。
3. **提示词指纹会随提示词改动而变化**：这是 L2 的核心机制，不是噪声。见
   `evals/baselines/v1.json` 里的 `prompt_digests`（16 项：12 份 base + packs）。
4. **未覆盖的平台**：评估跑在 stdio/HTTP 之外的纯逻辑层，不验证云端平台的接入行为
   （那些见 [`integrations/`](integrations/)）。
